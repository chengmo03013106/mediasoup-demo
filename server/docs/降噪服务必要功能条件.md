# 降噪服务必要功能条件文档

> 版本：v1
> 日期：2026-08-24
> 用途：明确自研降噪服务要接入本 SFU 闭环，必须满足的功能与协议条件。

---

## 一、降噪服务定位

降噪服务是一个**独立的 UDP + HTTP 客户端服务**，职责是：

1. 接收 SFU 旁路推来的 opus RTP 音频流。
2. 解码 → 降噪（RNNoise）→ 编码。
3. 以固定 SSRC 回传降噪后的 opus RTP 给 SFU。

> 技术更正：RNNoise 不是"大模型"，而是 Xiph/Jean-Marc Valin 开发的**轻量实时降噪库**（小 RNN + DSP，权重仅几十 KB，总延迟 < 30ms）。它恰好适合本实时场景。

---

## 二、必须满足的功能条件（硬性）

### 条件 1：能接收 UDP RTP（旁路方向）

- 降噪服务监听一个**固定 UDP 端口**（如 5000），SFU 会 `connect` 到这个 `ip:port`。
- 接收的媒体：`audio/opus`，48kHz，RTCP-mux（RTP 和 RTCP 走同一端口）。
- 需要能解析 RTP 包头（SSRC、PT、timestamp、seq）和 opus payload。

### 条件 2：opus 解码 → PCM

- 将 opus 解码为 PCM，供 RNNoise 处理。
- 采样率 48kHz。

### 条件 3：RNNoise 降噪

- 逐帧处理，帧长 **480 采样（10ms）** 或 **960 采样（20ms）**，保持帧对齐。
- 延迟必须**恒定**（RNNoise 天然满足，< 30ms）。
- 输出 PCM 与输入**帧数一致**（输入 N 帧 → 输出 N 帧），不丢帧、不插帧。

### 条件 4：PCM → opus 编码

- 将降噪后的 PCM 编码回 opus。
- **关键**：opus 的 fmtp 参数（complexity、stereo/mono、maxplaybackrate 等）需与上游尽量一致。**注意 RNNoise 只支持单声道（mono）**，若上游是 stereo（`channels:2`），降噪服务需先 downmix 到 mono 处理，再决定输出 mono 还是 stereo（本项目调试阶段，输出 mono 即可，但要在回传 producer 的 codec 参数里声明 `channels:1`）。

### 条件 5：回传 RTP 头重建（这是最关键条件）

降噪后回传时，RTP 包头**必须由降噪服务自己重建**，不能原样透传上游包。具体要求：

| 字段 | 要求 |
|------|------|
| **SSRC** | 由降噪服务自定，在 `produce` 请求的 `rtpParameters.encodings[0].ssrc` 里声明（BroadcasterPeer 流程） |
| **Payload Type** | 与 `produce` 请求里 `rtpParameters.codecs[].payloadType` 一致（降噪服务自定，需 96-127 区间） |
| **Timestamp** | 48kHz 时钟，每帧递增 960（20ms 帧）或 480（10ms 帧），**连续递增** |
| **Sequence Number** | 独立从 0（或随机）开始，**单调递增**，不复用上游 seq |
| **Marker bit** | 按 opus 惯例，每帧首个包置位 |

> 为什么必须重建：上游的 SSRC/seq/timestamp 语义已被"降噪打断"（重编码改变了帧内容与时机）。回传 SSRC/PT 由降噪服务在 `produce` 时声明，与发包时的 RTP 头一致即可。

### 条件 6：静音期行为（跟随上游）

- 上游 DTX 静音不发包 → 降噪服务收不到包 → **降噪服务也不发包**（跟随上游）。
- 恢复发包后，降噪服务恢复处理并回传。
- RNNoise 对"断流后恢复"的第一帧可能有极轻微 overlap 缺失，听感基本无感，可接受。

### 条件 7：以 BroadcasterPeer 身份加入房间（HTTP 客户端）

降噪服务需通过 **HTTP API** 主动加入房间（这样才能在前端生成独立 peer 条目，实现 A/B 分路）：

1. `POST /rooms/:roomId/broadcasters/denoiser` — 创建 BroadcasterPeer
2. `POST /rooms/:roomId/broadcasters/denoiser/join` — 加入房间
3. `POST /rooms/:roomId/broadcasters/denoiser/plain-transports` — 建回传 transport（返回 SFU 分配的 ip/port）
4. `POST /rooms/:roomId/broadcasters/denoiser/plain-transports/:id/connect` — connect 到降噪服务地址
5. `POST /rooms/:roomId/broadcasters/denoiser/plain-transports/:id/produce` — 回传 produce（声明 SSRC/PT/codec）

> 说明：回传端口由 SFU 分配、API 返回（BroadcasterPeer 标准流程）。降噪服务需按第 3 步返回的 `port` 发包，并在第 5 步 `produce` 时声明与发包一致的 SSRC/PT。

## 三、可以暂缓/不做的事项

- ❌ RTCP 回传（暂缓）
- ❌ 健康检查重连（先手动重启）
- ❌ 多路并发、背压
- ❌ 视频处理

---

## 四、最小验收标准（降噪服务侧）

- [ ] 能收到 SFU 旁路的 opus RTP（抓包或日志确认）
- [ ] 解码 → RNNoise → 编码链路跑通，无崩溃
- [ ] 回传 RTP 的 SSRC/PT 与 `produce` 声明一致，timestamp 连续递增
- [ ] 观察端出现"denoiser"独立音频条目，且能听到降噪后声音
